1. ملخص تنفيذي

تم بناء إطار أتمتة اختبارات متكامل لمنصة سلامات يغطي واجهة المستخدم (E2E) والـ API، ويعمل محليًا وعلى GitHub Actions. يتناول التقرير حالة المشروع الحالية، ثم يقيّم أداة e2e كإضافة محتملة لتقليل تكلفة صيانة الاختبارات.

3. بنية الإطار

  • نمط Page Object Model: فصل منطق الصفحات عن الاختبارات لسهولة الصيانة.
  • Fixtures مشتركة وجلسة دخول مشتركة بين الـ workers لمنع فتح متصفحات متعددة.
  • أدوات مساعدة: التعامل مع Excel، تسجيل استدعاءات الـ API، ودعم العربية في الـ terminal.
  • أدلة عند الفشل: لقطة شاشة + فيديو + Trace، وتقرير HTML تلقائي.
  • CI: تشغيل تلقائي على GitHub Actions مع إعادة المحاولة مرتين، وبيانات الاعتماد خارج الـ git.

4. أداة e2e: ما هي؟

إطار اختبار حديث (e2e-inc/e2e على GitHub، رخصة Apache-2.0) للويب والموبايل. تصف الهدف بلغة طبيعية ويقوم وكيل ذكاء اصطناعي بتنفيذه على التطبيق، ويمكن إضافة locators وassertions للتحقق من النتيجة. الخطوات التي يتبعها assertion تُسجَّل وتُعاد من دون استدعاء الموديل حتى يتغير التطبيق. محرك الويب مبني على Playwright. التثبيت: npx e2e init.

5. الفوائد المتوقعة

  • تقليل وقت صيانة الاختبارات عند تغيّر الواجهة (الفلاتر، خطوات إنشاء الحملات).
  • كتابة أسرع للسيناريوهات الطويلة الجديدة.
  • تشغيل متكرر في CI بتكلفة موديل منخفضة بعد التسجيل.
  • إمكانية تغطية تطبيق الموبايل بنفس الأداة.

6. المخاطر والقيود

  • أداة جديدة تحتاج تعلّمًا وصيانة بجانب Playwright.
  • الوكيل قد يتخذ مسارًا ينجح فيه الاختبار وهو غير المقصود، لذا نحتاج assertions قوية.
  • تكلفة tokens عند التسجيل الأول، ومتطلب موديل (اشتراك أو API key).
  • التوثيق الذي اطلعنا عليه لا يوضح إمكانية دمجها مع مشروع Playwright قائم، وهذا يحتاج تجربة فعلية.

7. التوصية والخطوات التالية

الإطار الحالي مستقر ومغطٍّ للوحدات الرئيسية، فلا حاجة لاستبداله. نوصي بإجراء تجربة محدودة (PoC) لأداة e2e في فرع منفصل:

  1. اختيار سيناريوهين: تسجيل الدخول، وفلتر العملاء.
  2. تنفيذهما بـ e2e ومقارنتهما بالحاليين في الاستقرار ووقت الكتابة وتكلفة الـ tokens.
  3. قياس الأداء عند تغيير الواجهة عمدًا.
  4. رفع القرار النهائي (اعتماد / اعتماد جزئي / عدم اعتماد) بعد النتائج.
